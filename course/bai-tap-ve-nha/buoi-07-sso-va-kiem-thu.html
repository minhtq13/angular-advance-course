Phần 0 · Khởi động: viết ra giấy (4 phút)

  1. Trong Authorization Code + PKCE, code_verifier nằm ở đâu, code_challenge đi đâu? Vì sao SPA cần PKCE?
  2. ID token và access token khác nhau ở aud thế nào? Token nào gửi cho API?
  3. Vì sao xóa token trong sessionStorage chưa phải là đăng xuất SSO?
  4. Kể 4 tầng của tháp kiểm thử Care Portal, mỗi tầng một ví dụ test đã có.
Ôn lại sau khi đã viết xong
CâuÝ chính
1code_verifier ngẫu nhiên, chỉ nằm trong tab; code_challenge = SHA256(verifier) đi kèm /auth. Khi đổi code ở /token phải gửi verifier. Client public không giữ được secret, nên code bị lộ cũng vô dụng.
2ID token: aud = care-portal (app), typ: ID. Access token: aud = care-api, typ: Bearer. API nhận access token; gửi ID token → 401 The aud claim is not valid.
3Phiên SSO nằm ở Keycloak (cookie KEYCLOAK_IDENTITY). Bấm SSO lần sau, Keycloak thấy phiên còn → trả code ngay. Phải RP-initiated logout: revoke token, end_session_endpoint với id_token_hint.
4Unit quy tắc (canApprove), integration HTTP + state (ticket-approval.spec.ts, oidc-auth.service.spec.ts), API trực tiếp (role-denial.spec.ts, ma trận buổi 6), E2E hành trình (ticket-approval.journey.spec.ts, sso.spec.ts).

Phần 3 · Vận dụng: giao phiếu cho nhân viên khác (10 phút)

Tính năng mới: Manager giao phiếu cho một agent khác; agent chỉ được tự nhận phiếu chưa có người xử lý. Phiếu đã đóng không giao được. Hiện tại PATCH /api/tickets/{id} nhận trường assignee từ bất kỳ ai đã đăng nhập (đọc TicketService.update).

  1. Viết quy tắc thành một hàm thuần canAssign(ticket, roles, currentUser, newAssignee) và ít nhất 6 dòng bảng it.each (trạng thái × vai trò × người được giao).
  2. Một integration test (TestBed + HttpTestingController) cho màn hình giao phiếu: kể 4 assertion cụ thể (URL, body, request tiếp theo, chữ trên màn hình). Mỗi assertion bắt được lỗi gì nếu code sai?
  3. Ba test gọi thẳng API (Playwright request) chứng minh server từ chối sai quyền, kèm kỳ vọng status và dữ liệu sau khi gọi.
Đáp án tham khảo (chỉ mở sau khi đã viết)
  1. Ví dụ: CLOSED + bất kỳ → false; SUPERVISOR + RESOLVED/NEW + giao cho agent2 → true; AGENT + phiếu chưa ai nhận + giao cho chính mình → true; AGENT + phiếu chưa ai nhận + giao cho agent2 → false; AGENT + phiếu đã của agent2 + giao cho mình → false; vai trò rỗng → false.
  2. expectOne(.../api/tickets/42) method PATCH (sai endpoint); body { assignee: 'agent2', version: 3 } (gửi nhầm người, version cũ); sau khi xong có một request tải lại đúng bộ lọc (quên reload); thông báo "Đã giao phiếu TK-000042 cho agent2" và khi 409 hiện lý do từ server (nuốt lỗi). Kết thúc bằng http.verify().
  3. AGENT giao phiếu của mình cho agent2 → 403, assignee không đổi; AGENT nhận phiếu đã thuộc agent2 → 403 (hoặc 409), vẫn của agent2; SUPERVISOR giao phiếu CLOSED → 409, version không đổi. Thêm một dòng đúng quyền (SUPERVISOR giao phiếu NEW → 200) để chắc test không đỏ vì lý do khác.

Phần tùy chọn · Soi SSO trên máy bạn

Chạy session07-end với --profile sso và config.json chế độ OIDC. Đăng nhập agent1, trong Network tìm response của POST .../token: giải mã id_token và access_token, ghi exp − iat, aud, các claim chỉ có ở một bên. Rồi đăng xuất và ghi thứ tự request tới localhost:8180. Không gửi token thật của hệ thống công ty.
